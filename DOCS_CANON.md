# Documentation Canon (cross-project)

Кросс-проектный канон продуктовой документации и лицензионной секции.
Живёт **только** в `/opt/standards`, не внутри продуктовых репозиториев.

Эталонный пример применения:

- README: `/opt/bots/watchdog_bot/README.md` (GitHub: `kartuznik/watchdog_bot`)
- LICENSE: `/opt/bots/watchdog_bot/LICENSE` (MIT)

## 1. Канон README

README продуктового репозитория — **технический и продуктовый** документ. Он должен быть честным, воспроизводимым и пригодным для портфолио.

### Обязательные блоки

1. **Краткий one-liner + badges** (стек, лицензия).
2. **Продуктовый паспорт в шапке** (сразу под badges / one-liner):
   - **Уровень сложности** по §5 (`Level 1` / `Level 2` / `Level 3`);
   - **Статус** продукта (`active` / `inactive` / `sale-freeze` и аналоги);
   - **Однострочная ценность** (зачем продукт пользователю/покупателю).
3. **О проекте** с честным scope:
   - **Что умеет** — рабочие возможности текущего кода.
   - **Чего не умеет** — явные границы (не enterprise «из коробки», не multi-tenant SaaS, если это так).
4. **Быстрый старт** — минимальный путь от clone до `docker compose up` (или честный путь продукта, если compose ещё нет — без ложного Docker-badge).
5. **Архитектура** — **только Mermaid** (flowchart/sequence). Без ASCII-схем как основного описания и без привязки к конкретным IP/хостам сервера. При правках README **не ломать** существующие Mermaid-диаграммы: переносить/адаптировать, не удалять ради «красоты».
6. **Возможности / ключевые фичи** — коротко, по факту кода.
   - Если у продукта есть **админка** (веб или privileged Telegram) — разбивать возможности на блоки **для клиента** и **для администратора**.
7. **Коммерческая модель (если есть монетизация в продукте)** — описывать **периодами и составом** (например «пробные генерации → подписка на неделю / месяц»), **без денежных сумм**, с явной пометкой: конкретные условия и цены живут **вне git**.
8. **Self-heal / graceful degradation (пользовательски)** — обязательный абзац или подпункт: что бот/сервис делает при недоступности внешних API (LLM, платежи, поиск и т.д.), авто-рестарте контейнера/systemd, лимитах. Только по факту кода — без выдуманного self-heal.
9. **Демо** — секция с плейсхолдерами под скриншоты/GIF (например `docs/demo/*.png`), которые владелец добавит позже. Пока файлов нет — список ожидаемых сцен.
10. **Переменные окружения** — имена и назначение, **без секретов и без реальных значений** (в т.ч. без примеров вроде `Admin123!`).
11. **Мониторинг / операции** — порты сервисов как *role ports* (например Grafana `:3001` или admin `:8005`), ссылка на runbook.
12. **Backup / restore** — краткий указатель в README со ссылкой на раздел backup в `docs/RUNBOOK.md` (детали только в runbook).
13. **Дата актуализации** README + указатель на changelog продукта (файл `CHANGELOG.md`, секция Changelog в README или git history — что принято в репо).
14. **FAQ** — 3–6 практических вопросов (scope, зависимости, типовые сбои).
15. **Ссылка на runbook** — `docs/RUNBOOK.md` (deploy, backup, key rotation, incidents, rollback) без секретов и адресов сервера.
16. **AI-инструменты** — обязательная секция после «Тестирование» и перед «Лицензирование и коммерческое использование»: перечень AI-инструментов разработки, которые реально использовались (агент, координирующий ассистент и аналоги). Если AI не использовался — честная строка об этом. Выдуманные инструменты запрещены. Эталон заполнения — README `kartuznik/todolist_test`, секция «AI-инструменты»: «Интерфейс собран в Cursor cloud agent. Координацию вёл ассистент Qwen.» В другом репозитории эту пару не подставлять.
17. **Лицензирование и коммерческое использование** — см. канон лицензии ниже.
18. **License** — ссылка на файл `LICENSE`.

### Языковая нормализация

- **Вся продуктовая документация** (README, `docs/RUNBOOK.md`, прочие файлы в `docs/` операционного характера) пишется на **русском** как основном языке.
- **Английский** допускается только в именах технологий, команд CLI, переменных окружения, идентификаторах API, метрик/алертов и цитатах из кода.
- Mermaid-диаграммы сохраняются; подписи узлов можно оставлять на EN, если так читаемее для стека, либо делать двуязычно — без ломки структуры графа.
- **Вторая языковая версия не ведётся проактивно**: параллельные переводы неизбежно расходятся и устаревают. Перевод на английский (или иной язык) выполняется **под конкретного международного клиента** как часть сделки редакции **Custom**, а не как постоянный twin-док в репозитории.

### RUNBOOK и операционная документация — русский

- `docs/RUNBOOK.md` и вся прочая **операционная** документация продукта пишутся на **русском** как основном языке (см. языковую нормализацию выше).
- Английский допускается **только** в именах команд (`docker compose`, `git`, …), переменных окружения, технологий, метрик/алертов и путях файлов.
- Существующие англоязычные RUNBOOK подлежат **ретро-переводу**, начиная с эталонного продукта (Watchdog Bot), затем остальные по очереди АПРУВ.
- Если каталог `docs/` также хранит **пользовательские аплоады** (PDF/MD корпуса), ops-файлы (`RUNBOOK.md`, `demo/`) не смешивать с аплоадами по смыслу: аплоады не править при docs-задачах; в `.gitignore` явно разрешить трекинг ops-файлов.

### Запрещено в README продуктового репозитория

- Цены, тарифы, денежные суммы, валютные символы в коммерческом смысле.
- Секреты, токены, пароли, приватные IP как «канонический» адрес доступа.
- Заявления «production-ready enterprise», если код — portfolio MVP.

### Рекомендуемый тон

Честный portfolio / self-hosted MVP. Можно говорить о soft-B2B возможностях (usage, export, alerts), не выдавая их за полноценную коммерческую платформу.

## 2. Канон лицензии (секция в README + файл LICENSE)

### Файл `LICENSE`

Базовая лицензия кода — **MIT**.

- Файл `LICENSE` в корне репозитория **всегда** остаётся **каноническим английским** текстом стандартной MIT-лицензии.
- Причины: GitHub определяет тип лицензии и вкладку *MIT License* по английскому тексту; перевод создаёт юридическую двусмысленность и ломает детект.
- **Не переводить** `LICENSE` на русский и не дублировать полный юридический текст по-русски в корне.

### Секция README: «Лицензирование и коммерческое использование»

Русский слой лицензирования и коммерции живёт **только** здесь (не в файле `LICENSE`).

Обязательные смыслы:

1. Базовая лицензия репозитория — **MIT**: код можно изучать, форкать и запускать self-hosted.
2. Коммерческие условия и редакции доступны **по запросу через контакт**.
3. Редакции описываются **по составу возможностей**, без денежных цифр.
4. Явная пометка: **конкретные цены и коммерческие условия живут вне продуктового git** (презентации, листинги, отдельные коммерческие материалы).

### Редакции (ориентир по возможностям)

| Редакция | Состав (ориентир) |
|---|---|
| **Community (MIT)** | Self-host продукт, базовый функционал репозитория, локальный мониторинг по возможности стека |
| **Starter** | Community + сопровождение внедрения single-tenant demo |
| **Team** | Soft-B2B admin (usage/export/retention и аналоги), operational alerts, runbook |
| **Custom** | Индивидуальный scope: Postgres/tenancy/SSO/интеграции — обсуждается отдельно |

Имена редакций можно адаптировать под продукт, но принцип «состав без цен» обязателен.

## 3. Freshness retrieval pattern (обязательный для веб-поиска)

Для всех будущих продуктов с live web search (Tavily и аналоги) действует единый паттерн свежести:

1. **Детектор маркеров актуальности на этапе retrieval** (не только в Reviewer):  
   `сегодня`, `сейчас`, `последн`, `текущ`, `свеж`, `today`, `latest`, `current`, `live`, `breaking` и аналоги.
2. **Вызов поиска:** `topic=news` + окно `days` (стартовый дефолт **2 дня**, конфигурируемо).  
   Если `days` дал пустую выдачу — **fallback** `start_date = today − window` (и/или расширение окна с логом).
3. **Пост-фильтр:** парсить `published_at` / даты из сниппетов, **ранжировать по свежести**; отбрасывать старше окна, если есть хотя бы один свежий; иначе оставить лучшие и залогировать **деградацию свежести**.
4. **Честная генерация:** если запрос про «сегодня», а самый свежий источник старше окна — ответ **явно помечает дату данных**, не выдавая старые события за текущие.
5. **Логи:** `tavily_days` (или эквивалент) и `source_date_range=min..max`.

Эталон реализации: Watchdog Bot (`agents/freshness.py`, `agents/web_search.py`, секция Freshness retrieval в README).

## 4. Self-diagnostics and Self-heal pattern (обязательный)

Обязательный ops-паттерн для **всех** наших продуктов (Level 1–3). Цель: владелец узнаёт о деградации раньше пользователя, сервис умеет ожить сам, внешние API не роняют продукт молча.

### 4.1 Команда `/health` или `/status`

Должна возвращать краткий снимок:

- БД (reachable / WAL или эквивалент);
- Telegram API (getMe / probe);
- диск / data volume (free space или ok/fail);
- внешние API по факту продукта (LLM primary/secondary, search, Redis/queue и т.д.).

Доступ — по RBAC продукта (обычно admin/owner). Не светить секреты и полные URL ключей.

### 4.2 Фоновый `health_check_loop`

- Периодический опрос (порядок минуты, конфигурируемо).
- При деградации — **алерт владельцу в Telegram** (in-bot и/или Grafana contact point).
- Не спамить: debounce / повтор с интервалом; логировать причину.

### 4.3 Авто-рестарт при падении

- Сервис должен подниматься через **systemd** (`Restart=`) и/или Docker `restart: unless-stopped` — что является стандартом деплоя продукта.
- Критичный crash loop — алерт владельцу; не маскировать бесконечный рестарт как «всё ок».

### 4.4 Graceful degradation внешних API

- **LLM:** fallback OpenAI ↔ DeepSeek (или принятая пара провайдеров) при 401/402/403 / balance; метрика fallback; честный лог.
- **Веб-поиск:** невалидный/отсутствующий ключ → soft-fail / skip search, продукт продолжает работать на допустимом режиме; пользователю — honest note, не generic crash.
- Другие внешние зависимости — по тому же принципу: degrade, не silent wrong answer.

### 4.5 Prometheus / observability

- Счётчики ошибок запросов и событий самодиагностики (health fail, restart, fallback, search soft-fail).
- Алерты на рост ошибок / очередь / LLM degrade — по канону alerting продукта.

Эталон ориентира: Watchdog Bot (`health_check`, monitor loop, LLM fallback, Tavily soft-fail, Prometheus metrics).

## 5. Product complexity levels (выбор на проектировании)

Чтобы не натягивать LangGraph на простой FSM-бот, фиксируем **три уровня**. Уровень выбирается на этапе проектирования и **явно указывается в README** продукта (секция «О проекте» / архитектура).

| Level | Название | Архитектура | Когда выбирать | Примеры |
|---|---|---|---|---|
| **1** | Simple bot | FSM + роли/RBAC, **без** LangGraph | Каталог, опрос, заказ, линейные сценарии, мало «рассуждения» | ShopBot, SurveyBot |
| **2** | Smart assistant | Single-agent: память диалога + опциональный веб-поиск, без multi-agent графа | Персональный ассистент, Q&A с памятью, лёгкий search | Kuzya |
| **3** | Multi-agent research | LangGraph (router / researcher / writer / reviewer), ARQ/background worker, grounded search | Исследование, свежие новости, ревью качества, тяжёлые задачи | Watchdog Bot, будущие research-продукты |

### Критерии выбора (кратко)

- Нужны только кнопки/шаги/роли → **Level 1**.
- Нужны память и иногда поиск, один «мозг» достаточен → **Level 2**.
- Нужны маршрутизация сложности, заземление источников, ревьюер, фон → **Level 3**.

Запрещено: тащить Level 3 в Shop/Survey «на вырост» без продуктовой необходимости. Усложнение уровня — отдельное АПРУВ-решение Архитектора.

## 6. Форматирование `.env` и `.env.example`

Эталон структуры: Content Generator после удаления YandexGPT  
(`/opt/bots/content-generator-bot/.env.example`).

### 6.1 Структура файла

1. **Секции-разделители** из строк с `#` и `=`:

```env
# ==========================================
# TELEGRAM
# ==========================================
TELEGRAM_BOT_TOKEN=
```

2. **UPPERCASE-имена групп по назначению** (адаптировать набор под продукт):
   - `TELEGRAM`
   - `LLM PROVIDERS` (или `OPENAI` / `DEEPSEEK` — без российских LLM)
   - `PAYMENTS` (например YooKassa)
   - `WEB ADMIN PANEL`
   - `DATABASE & LOGS`
   - `MONITORING` (если есть Prometheus/Grafana/метрики)

3. **Полезные ссылки** — в комментариях **на отдельных строках** внутри секции (не в той же строке, что переменная).

4. **Одна переменная на строку**: `KEY=value`.

5. При рефакторинге форматирования серверного `.env` **значения не изменяются** (только структура/комментарии). Перед правкой — `.env.bak`; после — сверка отсортированных пар `ключ=значение`.

6. Секреты **не** коммитить; в `.env.example` — только имена и пустые/плейсхолдерные значения без реальных токенов.

### 6.2 Выбор LLM-провайдеров

- В продуктах **не используются российские LLM-платформы** (в т.ч. YandexGPT и аналоги).
- Допустимы **зарубежные** провайдеры: OpenAI, DeepSeek и подобные по решению Архитектора.
- **Мультипровайдерность** и выбор альтернатив (fallback-пары, роутинг) — осознанное отдельное решение, не default «подключить всё подряд».
- Устаревшие ключи/секции российских провайдеров удалять из кода, `.env` и `.env.example`, а не оставлять «на будущее» в документации продукта.
